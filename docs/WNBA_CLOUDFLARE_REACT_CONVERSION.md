# WNBA Predictions — Streamlit to React + Cloudflare Conversion Runbook

## Purpose

This document is a complete implementation brief for converting the existing `gmalbert/wnba-predictions` repository from a Streamlit-hosted application into a React application designed for Cloudflare hosting while preserving the existing Python modeling, data ingestion, prediction generation, validation, and GitHub Actions workflows.

The target architecture is intentionally **not** "Streamlit → FastAPI + React."

The preferred target is:

```text
GitHub Actions
    |
    |-- data ingestion
    |-- feature engineering
    |-- model training
    |-- model evaluation
    |-- prediction generation
    |-- odds snapshots
    |-- data-health generation
    |-- web-data export
    v
Cloudflare R2
    |
    v
React application
    |
    v
Cloudflare Pages
```

FastAPI should **not** be introduced unless a specific feature cannot reasonably be implemented using:

1. precomputed data generated by GitHub Actions,
2. browser-side React/TypeScript calculations, or
3. Cloudflare-native lightweight functionality.

The existing Streamlit site must remain intact during migration and must be treated as the reference implementation until parity is verified.

# 2. Migration Goal

The end state should provide **full functional parity and near-exact visual/design parity** with the public-facing Streamlit application while moving presentation and inexpensive interactivity into React.

For the initial migration milestone, the React implementation must reproduce the existing Streamlit application's design as closely as practical before any redesign or modernization work is attempted.

This means preserving, page by page:

- overall information architecture,
- page ordering,
- navigation structure,
- sidebar behavior,
- content hierarchy,
- section ordering,
- card placement,
- column proportions,
- metric placement,
- spacing and density,
- headings and subheadings,
- colors,
- probability bars,
- confidence badges,
- alert/warning presentation,
- table structure,
- chart type,
- chart ordering,
- chart dimensions where practical,
- labels,
- captions,
- typography hierarchy,
- borders,
- dividers,
- responsive behavior,
- empty states,
- error states,
- "No Bet" states,
- paper-only warnings,
- release-gate warnings,
- logo placement,
- Betting Oracle branding,
- WNBA-specific branding.

The objective is **not** merely "same data, different React design."

The objective is:

```text
existing Streamlit page
        ↓
React implementation
        ↓
visually and functionally recognizable as the same application
```

Small differences caused by browser rendering, framework defaults, or accessibility improvements are acceptable, but the coding model must not take design liberties during the parity phase.

Any substantial redesign, modernization, re-layout, or aesthetic reinterpretation must be deferred until after visual parity has been documented and accepted.

The migration must preserve:

- all model outputs,
- all WNBA-specific assumptions,
- all existing prediction logic,
- all data-quality safeguards,
- all release-gate logic,
- all "No Bet" / paper-only behavior,
- all confidence classifications,
- all model-performance metrics,
- all data-health reporting,
- all odds/provider provenance,
- all existing scheduled refresh behavior unless deliberately improved,
- all existing auditability and leakage-safety behavior.

The migration must **not**:

- silently rewrite the modeling system in JavaScript,
- perform model training in the browser,
- perform heavy pandas work in Cloudflare Workers,
- remove or weaken validation gates,
- expose sportsbook/data-provider secrets to React,
- call private provider APIs directly from the browser,
- require FastAPI merely to serve JSON files,
- replace working Python pipeline code without a clear reason,
- delete the Streamlit app before parity has been established.

# 4. Core Design Principle

Every existing Streamlit feature must be classified into one of four execution locations.

## A. GitHub Actions / Python pipeline

Use for:

- data scraping,
- API ingestion,
- historical refresh,
- odds snapshots,
- feature engineering,
- model fitting,
- calibration fitting,
- model validation,
- walk-forward validation,
- large backtests,
- generation of prediction artifacts,
- generation of data-health artifacts,
- generation of model-performance artifacts,
- computationally expensive simulations,
- production release-gate evaluation.

## B. Cloudflare R2

Use for generated production artifacts such as:

```text
predictions.json
standings.json
team_stats.json
player_stats.json
model_performance.json
data_health.json
release_gate.json
manifest.json
```

R2 is an object store, not an analytical database.

Do not design the React app around arbitrary R2 queries.

## C. React / browser

Use for:

- sorting,
- filtering,
- search,
- pagination,
- navigation,
- chart rendering,
- display formatting,
- confidence badges,
- UI state,
- simple arithmetic,
- odds conversions,
- small probability calculations,
- modest browser-side simulations where practical.

## D. Backend API

Initial target:

```text
NONE
```

Add one later only if a specific feature genuinely requires server-side request-time execution.

# 9. JSON Requirements

All exported JSON must:

- be deterministic,
- contain a schema version,
- avoid NaN and Infinity,
- use ISO-8601 timestamps,
- use stable keys,
- use canonical IDs where available,
- include source/provenance fields where useful,
- not expose secrets,
- not expose environment variables,
- not expose provider credentials,
- preserve explicit missing-data states,
- preserve `paper_only`,
- preserve `status`,
- preserve `no_bet`,
- preserve release-gate state.

Use strict JSON-safe conversion.

Convert:

```text
NaN -> null
NaT -> null
numpy types -> native JSON values
Timestamp -> ISO-8601 string
```

# 11. Scenario Lab Migration Strategy

Do not add FastAPI initially.

Port the Scenario Lab's lightweight numerical logic to TypeScript.

Before porting, inspect:

```text
utils/market_simulation.py
```

Create parity tests against Python.

For each browser-side calculation:

1. generate fixed test fixtures from Python,
2. store expected outputs,
3. implement TypeScript equivalent,
4. compare within defined numerical tolerance.

Recommended tests:

```text
player prop baseline
availability = 0
availability = 1
very low minutes
high uncertainty
high line
low line
three-leg positive correlation
zero correlation
negative correlation
near-singular correlation
```

If Monte Carlo is used, make results reproducible using a deterministic seeded PRNG.

Do not accept materially different outputs merely because both implementations are stochastic.

If exact parity is impractical:

- define an acceptable statistical tolerance,
- compare many seeded runs,
- document the difference.

Only introduce a backend if browser execution is proven unsuitable.

# 17. Release Gate

The current safety/release gate must remain authoritative.

The app must continue to respect conditions such as:

- untouched holdout availability,
- minimum priced paper-bet count,
- CLV threshold,
- feature drift limits,
- unresolved player availability,
- stale inputs,
- scenario uncertainty.

The frontend must not determine whether production betting is allowed.

The Python pipeline should emit the release-gate result.

React only displays the authoritative result.

Example:

```json
{
  "status": "shadow",

  "paper_only": true,
  "checks": {
```

# 22. Publishing Atomicity

Avoid exposing a partially updated dataset.

Preferred pattern:

1. upload versioned artifacts,
2. verify uploads,
3. update the small `manifest.json` last.

Example:

```text
wnba/releases/abcdef123/predictions.json
wnba/releases/abcdef123/standings.json
wnba/releases/abcdef123/...
```

Then:

```json
{
  "active_release": "abcdef123"
}
```

or publish a manifest pointing to that release.

React should fetch the manifest first.

This prevents mixed-generation data.

# 26. Reproduce the Streamlit Design, Not the Streamlit Runtime

For the parity milestone, reproduce the **visual layout and interaction pattern** of the Streamlit application as closely as practical.

Do not reproduce Streamlit's runtime mechanics such as full-script reruns, but do reproduce the user's visual experience.

Examples:

```text

-> React metric card that closely matches the existing size, spacing, typography, and placement

st.dataframe
-> React table preserving the same columns, labels, density, ordering, and general visual treatment

st.selectbox
-> React select preserving the same label, location, default value, and role in the layout

st.tabs
-> React tabs preserving the same labels, order, and content grouping

st.warning / st.error / st.info
-> visually equivalent alert/banner with matching prominence and intent

st.navigation
-> React Router while preserving the same navigation hierarchy and visible page names

st.plotly_chart
-> frontend chart matching the same chart type, dimensions, labels, ordering, and presentation
```

Framework-specific behavior may change internally, but the visible result should remain close to the reference.

Do not use the React migration as an excuse to reorganize or reinterpret the UI.

This is critical.

Bad:

```text

-> Pages rebuild
```

```text

```

# 40. Cloudflare Workers

Do not add a Worker unless needed.

Acceptable future Worker uses:

- same-origin R2 proxy,
- cache-control normalization,
- authentication,
- lightweight request validation,
- CORS management,
- simple routing.

Do not use Workers Free for:

- pandas,
- model training,
- heavy Monte Carlo,
- large Python inference,
- backtesting.

# 41. FastAPI Decision Gate

FastAPI should only be introduced if a feature satisfies all or most of:

```text
must execute because of current user input
cannot reasonably run in browser
cannot be precomputed
requires existing Python-only logic
requires secrets
requires server-side persistence
requires large-data query reduction
```

For the initial WNBA conversion:

```text
FastAPI target = NONE
```

Document any feature that challenges this assumption.

The authoritative model remains Python.

The authoritative predictions remain Python-generated.

The authoritative release gate remains Python-generated.

The authoritative data-quality status remains Python-generated.

Do not create a second independent modeling implementation in TypeScript.

# 54. Coding Rules

While performing the migration:

1. Read the existing implementation before replacing behavior.
2. Reuse existing business logic whenever possible.
3. Do not invent new model behavior.
4. Do not alter prediction semantics merely to simplify React.
5. Avoid broad rewrites of Python pipeline code.
6. Keep commits/phases logically separable.
7. Add tests for every new boundary.
8. Keep generated artifacts deterministic.
9. Keep schema versions explicit.
10. Prefer small stable APIs/contracts between layers.
11. Avoid dependencies without a clear need.
12. Keep React components reasonably modular.
13. Do not add server infrastructure preemptively.
14. Preserve existing tests.
15. Record architectural decisions in documentation.
16. Treat the existing Streamlit design as the visual source of truth during the parity phase.
17. Do not redesign, modernize, simplify, or reorganize page layouts before visual parity is achieved.
18. Capture reference screenshots before making substantial React styling decisions.

# 58. Final Architecture Goal

The final WNBA application should look conceptually like:

```text
                      GitHub Actions
                           |
            +--------------+--------------+
            |              |              |
            v              v              v
         ingest          train          predict
            |              |              |
            +--------------+--------------+
                           |
                           v
                  export_web_data.py
                           |
                           v
                versioned JSON release
                           |
                           v
                    Cloudflare R2
                           |
                           v
                   Cloudflare CDN
                           |
                           v
                    React / Pages
                           |
                           v
                         User
```

with:

```text
Streamlit = retained reference / fallback during migration
FastAPI   = not required initially
D1        = not required initially
Workers   = optional later
```

```text
GitHub Actions for compute
Cloudflare R2 for generated data
React for UI
Cloudflare Pages for hosting
```

while retaining full analytical and operational correctness.
